## 학습 범위

‘깔끔하게’, ‘자연스럽게’ 같은 표현은 방향을 전달하지만 완료 조건으로 쓰기 어렵다. 화면 요소, 상태 변화, 확인 방법까지 정리해야 구현 결과를 비교할 수 있다.

코드깎는노인의 UI·모션 용어 영상에서 학습 주제를 골랐다. 검토한 설명·챕터 기록은 움직임을 구체적인 이름과 요청 예시로 다루고 있다. **영상 전체를 시청하거나 자막 전체를 검토한 글은 아니다.** 아래 요청문과 검증 항목은 별도로 구성했다. [참고 영상: 필수 용어 24가지 2탄](https://www.youtube.com/watch?v=r7iS0Gw3Jq4)

## 대상·상태·결과로 작성

이 홈페이지의 모노톤 변경 요청을 예시로 정리하면 다음과 같다.

```text
대상: 홈, 글 목록, 글 본문, 프로젝트 시연
색상: 흑백·회색 계열
테마: 기기의 라이트·다크 설정에 맞춰 자동 전환
상태: 버튼 기본·호버·키보드 초점, 입력 오류
문구: 제목과 안내는 짧게, 본문은 간결한 평서문
확인: 모바일과 데스크톱, 두 테마에서 읽기·조작 가능
```

‘다크 모드 지원’만 적으면 저장 방식이나 전환 시점이 모호하다. 이 예시는 수동 선택이 아니라 기기 설정을 따르는 방식이다. 브라우저가 사용자의 테마 선호를 전달하면 CSS의 `prefers-color-scheme`으로 대응할 수 있다. [MDN — prefers-color-scheme](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/At-rules/@media/prefers-color-scheme)

## 모션 요청에 필요한 조건

움직임은 이름만 고르지 않고 시작 조건과 종료 상태를 함께 적는다. 다음은 연습용 버튼 요청이다. 이 사이트에 새 애니메이션을 추가했다는 의미는 아니다.

- 대상: 프로젝트 이동 버튼.
- 시작 조건: 마우스를 올렸을 때.
- 변화: 배경색만 변경. 크기와 위치는 고정.
- 시간: 150ms를 초기값으로 사용.
- 키보드: 초점 테두리로 현재 위치 표시.
- 모션 감소 설정: 전환 효과 없이 상태만 변경.

150ms는 이 실습의 초기값이며 모든 화면에 맞는 정답은 아니다. 읽기와 조작을 방해하는지 확인한 뒤 조정한다.

`prefers-reduced-motion`은 사용자의 모션 감소 설정을 감지한다. 이 설정을 사용할 때도 버튼의 상태 변화와 필요한 정보는 유지해야 한다. [MDN — prefers-reduced-motion](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/At-rules/@media/prefers-reduced-motion)

## 확인 항목

요청의 각 조건을 관찰 가능한 결과로 바꾼다.

1. 라이트·다크에서 제목, 본문, 입력값을 읽을 수 있는가.
2. 기기 테마 변경 후 화면이 따라 바뀌는가.
3. 좁은 화면에서 가로 넘침이나 버튼 잘림이 없는가.
4. 키보드만으로 링크와 입력창에 접근할 수 있는가.
5. 오류를 색상 외의 문구나 형태로도 구분하는가.
6. 모션 감소 설정에서 불필요한 전환이 제거되는가.

스크린샷은 배치와 색상 확인에 사용한다. 검색, 입력, 초점 이동 같은 동작은 직접 조작해 확인한다.

## 이 사이트에서 확인한 범위

모노톤 변경에서는 Chrome의 화면 너비와 색상 환경을 바꿔 라이트·다크 표시를 확인했다. 새로고침 없는 테마 전환, JavaScript 없는 다크 모드, 주요 텍스트 대비, 검색과 실패 시연도 검증했다.

실물 모바일 기기에서 같은 검사를 한 것은 아니다. 브라우저 에뮬레이션 결과와 실제 기기 검증은 구분한다. 위의 버튼 모션 실습은 별도 연습 과제로 남긴다.
