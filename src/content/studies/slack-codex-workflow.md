## 무엇을 연결하려는가

AI 도구에 코드를 요청하는 것과, 여러 프로젝트의 작업 맥락을 이어가는 것은 서로 다른 문제다. 요청은 대화에, 코드는 저장소에, 설계 이유는 문서에 남는다. 이 프로젝트에서는 **Slack을 작업의 입구로, Codex를 프로젝트 작업의 실행 주체로** 연결하는 구성을 사용한다.

목표는 모든 일을 무조건 자동화하는 것이 아니다. 어떤 프로젝트의 요청인지, 어떤 대화에서 이어진 일인지, 무엇을 실제로 확인했는지를 연결하는 데 있다. 이 글은 현재 운영 규칙과 채널 연결 인계 기록을 바탕으로 정리한 설계 설명이며, 실시간 상태 보고서는 아니다.

## 관리·프로젝트·작업의 범위를 나누기

대화의 범위를 세 단계로 나눈다.

- **관리 DM:** 전체 프로젝트 관리와 작업 전달.
- **프로젝트 채널:** 연결된 프로젝트의 요청과 논의.
- **Slack 스레드:** 하나의 독립된 작업 대화. 후속 요청도 같은 맥락에서 이어간다.

예를 들어 같은 프로젝트에서 메뉴 수정과 API 설계가 동시에 진행된다면, 서로 다른 스레드에서 다룬다. 반대로 메뉴 수정의 추가 요구나 검증 결과는 기존 메뉴 작업 스레드에 이어간다.

브리지는 이런 연결 관계를 유지해야 한다. 아래는 실제 내부 ID가 아닌 관계를 설명하기 위한 예시다.

```text
project-channel
  ├─ thread-A → navigation-task
  └─ thread-B → api-design-task
```

대화가 독립적이라고 해서 공유 저장소까지 서로 무관한 것은 아니다. 같은 파일을 수정하는 작업은 조정하고, 다른 작업자가 남긴 변경을 보존해야 한다.

## 실행 전에 완료 조건을 정하기

짧은 요청을 받았을 때 먼저 입력과 기대 결과를 구체화한다. 예를 들어 “모바일 메뉴를 추가해줘”라는 요청에는 다음과 같은 확인 항목을 붙일 수 있다.

1. 작은 화면에서도 메뉴 버튼이 보이는가?
2. 메뉴를 열고 링크를 선택할 수 있는가?
3. 키보드만으로 조작할 수 있는가?
4. 기존 데스크톱 탐색은 유지되는가?

이 목록은 예시이며, 매 작업에 같은 테스트를 기계적으로 적용한다는 뜻은 아니다. 프로젝트 지침과 기존 소스, 변경 상태를 먼저 확인하고 요청에 맞는 완료 조건을 정한다.

## 코드 작성과 검증 결과는 구분하기

파일을 수정한 것은 구현 단계의 결과다. 실제 실행과 검증까지 통과했다고 말하려면 각각의 근거가 필요하다.

- 코드 수정: 어떤 파일과 동작을 바꿨는지.
- 실행 확인: 프로그램이나 페이지가 실제로 실행됐는지.
- 검증: 어떤 조건으로 확인했고 무엇이 통과하거나 실패했는지.
- 전달: 결과가 전송됐는지. 사용자가 열람했는지와는 별개다.

검증에 실패하면 실패 조건을 기록하고 수정한 뒤 같은 조건으로 다시 확인한다. 아직 확인하지 못한 결과는 완료로 표시하지 않는다. 공개 배포나 삭제처럼 영향이 큰 작업은 일반 개발 작업과 승인 범위를 구분한다.

## 웹에서 보여줄 수 있는 범위

[프로젝트 페이지의 흐름 체험](/projects/slack-codex/#demo)은 접수·맥락 확인·검증·보고의 네 단계를 보여준다. 정상 흐름과 검증 실패 흐름을 선택할 수 있다.

이것은 **미리 작성된 메시지로 구성한 모의 시연**이다. 입력은 브라우저 화면에만 표시되고 Slack으로 전송되지 않는다. Codex 실행, 실제 파일 변경, AI 호출도 발생하지 않는다.

기존 쇼케이스 검증에서는 화면 크기별 표시, 키보드 조작, 공백 입력, HTML 문자열의 텍스트 표시 등을 확인했다. 이 결과는 웹 시연의 검증 근거이며 실제 Slack–Codex 시스템 전체의 성능이나 안정성을 증명하지 않는다. 실제 실행 영상과 시스템 전체 검증 결과는 별도로 준비할 항목이다.

## 기록과 공개 콘텐츠의 역할

Notion에는 조사, 설계 초안, 진행 기록과 결정의 이유를 남긴다. GitHub에는 소스와 변경 이력을 남긴다. 이 사이트에는 외부에서 읽을 수 있도록 정리한 글과 프로젝트 소개를 발행한다.

내부 문서를 그대로 복사하지 않고, 공개해도 되는 설명과 예시를 선택한다. 실제 서비스 계정, 인증정보, 내부 채널 주소는 공개 시연에 필요하지 않다.

다음 학습 과제는 실제 요청과 결과의 경계를 관찰할 수 있는 검증 사례를 더 모으는 것이다. 측정하지 않은 시간 절감이나 생산성 향상 수치는 붙이지 않는다.
